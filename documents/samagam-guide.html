Part 1 — The basics

1

What this app actually is

In one sentence

One piece of software, used by about 1,350 different schools and offices, where each one gets its own separate database.

Samagam is built for Kendriya Vidyalaya Sangathan. Think of KVS as a big organisation with a head office, regional offices, and lots of schools under them. About 55,000 employees in total.

Each organisation gets its own web address — a subdomain. Something like:

  • kvs.samagam.gov.in
  • dps.samagam.gov.in

Same code running behind both. Different data. The web address is how the system knows which one you mean. This matters more than it sounds — it's why you can log in with just your Employee ID and a password. You never pick your school from a dropdown, because the address already said it.

Words you'll hear a lot

tenant
One organisation. One school or office. The word comes from "multi-tenant software" — many customers sharing one app.
organisation / org
Same thing as tenant. The code uses both.
slug
The short name of an organisation, like kvs. It becomes the subdomain and the database name.
the platform
The shared parts everyone uses: gateway, login, screens.
a service
One backend program that handles one area — helpdesk, students, staff records.
the shell
The Next.js app that serves the screens. "Shell" because it's the outer frame everything else sits in.
2

Why each school gets its own database

In one sentence

Instead of putting a school ID column on every table and hoping nobody forgets it, each school gets a whole separate database — so forgetting is impossible.

This is the single most important idea in the whole system. If you understand nothing else, understand this.

That third lock is worth a closer look. Every time the code opens a connection to a school's database, the very first thing it does — before any of your queries — is ask the database a question:

SELECT tenant_key FROM authz.tenant_meta

The database answers with its own name, for example kvs. The code compares that to the school it thinks it's serving. If they don't match, it throws an error and nothing runs. So even if something upstream got confused, a wrong connection cannot serve wrong data.

The trade-off

1,350 databases is 1,350 things to migrate, back up and monitor. That's a real cost, and it's why there's a whole worker program (chapter 14) just for managing them. The team decided that cost is worth paying so that a leak between schools is structurally impossible rather than merely unlikely.

Part 2 — How a request travels

4

What happens when you open a page

In one sentence

Your browser asks the gateway, the gateway checks the school is allowed to be served, then hands the request to the Next.js shell, which sends back HTML and JavaScript.

If the school isn't ready, you don't get a page — you get a clear message from the gateway instead:

School statusWhat you seeWhy
activeThe pageNormal.
provisioning
awaiting_handover		503 — "being set up, not open yet"It's coming. Try later. (One exception: the handover link still works, or nobody could ever get in.)
suspended403 — "not available, contact your administrator"Not 404, because the people who work there know it exists and need to know who to ask.
draft, purged,
or anything unknown		404 — "no organisation at this address"Looks exactly like a typo. That's on purpose — the internet shouldn't be able to discover which schools exist.
5

What happens when a screen fetches data

In one sentence

The browser calls /api/helpdesk/tickets on the same address it's already on, the gateway sends it to the helpdesk service, and that service asks Auth whether you're allowed before it does anything.

Why not let the service decide?

Because then there would be two copies of the permission rules, and one day they'd disagree. When that happens you get a bug nobody can reproduce, in the part of the system where being wrong matters most. So: one place decides, everyone else asks.

6

The headers that travel with a request

In one sentence

The gateway adds a few headers that say "I checked this, and here's proof" — and every service downstream refuses to work without that proof.

Header cheat sheet

Host
The address the browser typed. This is what decides the school — but only after the registry confirms it.
x-forwarded-host
The gateway repeating the Host, so it survives Next.js re-rendering a page internally.
x-gateway-token
The proof. Means "the gateway really did set the line above."
x-internal-token
Means "I'm allowed to call this internal endpoint at all." Without it you get 404, not 401.
x-request-id
One ID for the whole request, minted at the gateway. It goes in the audit rows, so when someone says "it told me no", you can find the exact row that explains why.
7

How the gateway decides where to send things

In one sentence

It looks at the start of the path. /api/helpdesk/… goes to the helpdesk service. Anything it doesn't recognise goes to the shell.

Why this is clever

Because a prefix that isn't listed falls through to the shell, you can move one feature out of the shell into its own service gradually. Before the new SIS service exists, /api/sis/* goes to the shell like it always did. The day you deploy it, you add one entry and it starts going to the new service. Nothing else changes, and the browser can't tell the difference.

One path the gateway refuses on purpose

/internal/authorize — the endpoint services use to ask "may they?" — is not under /api/. The gateway only forwards /api/<key>/*, so there is no way for a browser to reach it, no matter how the request is shaped. That's not a rule someone has to remember; it's just how the routing works.

Part 3 — Who you are and what you may do

8

Logging in, step by step

In one sentence

You type an Employee ID and a password; the system checks them carefully and slowly on purpose, then gives your browser two cookies.

Why the fake password check?

Imagine the system replied instantly for an ID that doesn't exist, and took 300ms for one that does. An attacker could then find out which Employee IDs are real just by timing the responses — without ever guessing a password. So when the ID isn't found, the code verifies the given password against a throwaway hash anyway. Same work, same time, same answer. Nothing leaks.

How long does a session last?

Two numbers, and whichever runs out first wins:

  • 12 hours absolute. A school day is long, but not endless.
  • 90 minutes idle. Every request you make pushes this back. Walk away from a staffroom computer for two hours and you're signed out, even though the 12 hours hasn't passed.

The frontend gets both numbers so it can work out the real expiry itself: min(absoluteExpiresAt, lastRequest + 90 min).

9

The two cookies, taken apart

In one sentence

One cookie proves who you are and is checked against the database every time; the other is a short-lived copy of what you're allowed to do, purely to save queries.

What __Host- actually does

It's not decoration. When a cookie name starts with __Host-, the browser refuses to accept it unless it's marked Secure, scoped to path /, and has no Domain attribute.

That last part is the whole game. Every school is a subdomain of the same parent. If a cookie set by kvs.samagam.gov.in carried Domain=samagam.gov.in, the browser would send it to every school. The prefix makes that impossible — not by convention, but at the browser level, where no developer can accidentally undo it.

10

"Is this person allowed?" — how that gets answered

In one sentence

The service forwards your cookie to Auth and asks about one specific thing; Auth checks five things in order and sends back a full answer.

Why 200 for a refusal?

Because a refusal is a successful answer to a question. If Auth returned 403 here, the calling service couldn't tell "you may not" apart from "I couldn't ask". Those need different handling — one is shown to the user, the other is a dependency outage.

11

Postings — the part that surprises everyone

In one sentence

Your permissions don't come from who you are. They come from which chair you're currently sitting in.

This trips up every new developer, so it's worth going slowly.

One person can hold several posts at once. A teacher might be a PGT at one school and hold additional charge at a regional office. Those are two completely different levels of authority. The system never adds them together.

"Personal scope" is a place, not an error

Someone can be signed in and hold no active posting. The code calls this scope: 'self'. It doesn't mean "broken" or "logged out" — it means they have their own account and their own record, and nothing that comes from a chair, because they aren't sitting in one.

Write your screens for it as a real destination with things in it, not as a failure state.

Mistakes you will be tempted to make

if (designationCode === 'PRINCIPAL') — no. A job title is not a permission. The permission is a thing an administrator ticked on a dashboard, and only Auth knows whether they did.

Filtering rows by unitCode from the session — no. Which rows someone may see comes from the coverage on the verdict Auth sends back, worked out server-side.

Treating isHead: true as a grant — no. Heading a unit is a fact about a post, not a permission.

The rule underneath all three: nothing the browser holds is proof of anything. A screen uses it to decide what to draw. The service decides what actually happens.

12

Where permissions actually come from

In one sentence

An administrator builds a dashboard, ticks some permissions onto it, and assigns it to a designation or a specific post — and that's the only way anyone gets authority.

Two different questions

QuestionAskUsed for
"May they do this one thing?"may(), via /internal/authorizeGating an action. One node, one answer. Asked by the service doing the work.
"What do they hold at all?"GET /api/auth/navigationDrawing the menu. Returns held[], a list of action keys. A drawing hint, not proof.

These two can legitimately disagree. If a grant is revoked after your page loaded, the menu still shows a button and the service refuses it. That's normal. Your screen should render the 403 as a sentence, not crash.

Part 4 — The control plane

13

What the control plane is, and why it's separate

In one sentence

It's the admin tool that creates schools — a completely separate product with its own database, its own login, and no access to anybody's personal data.

There is one platform operator account for the whole system. That single fact drives the entire design of this part. The question the team asked was: if that one account gets breached, how far can the damage go?

The answer they engineered for: it stops at the registry. The attacker learns which schools exist. They do not learn who works there.

What the control plane database holds

TableWhat's in it
cp.tenantThe list of schools. Slug, display name, status, and the shape of their office hierarchy.
cp.tenant_domainWeb address → school. This is the row the gateway looks up on every request.
cp.tenant_databaseWhich database holds which school, which schema version it's on, and a pointer to where the password is kept — never the password.
cp.jobThe queue. Kind, school, payload, status.
cp.provisioning_run / _stepSetting up a school, step by step, so a run that dies at step 4 resumes at step 4 instead of starting over.
cp.platform_adminThe one operator account. Password + TOTP.
cp.audit_eventEverything that happened. Intent written before the act.
cp.worker_heartbeatProof the worker is alive, so "stopped on purpose" looks different from "died".
The rule that holds it all together

No tenant personal data. Ever. Not a name, not an email, not a mobile number, not a date of birth. The control plane knows a school exists and which database holds it. It does not know who works there.

14

How a new school gets created

In one sentence

An operator fills a form, which writes a row and drops a job on a queue; the worker picks it up and builds the database step by step; then a one-time link hands the school to its first administrator, and the door locks behind them.

What "sealing" means

Once a school has a real administrator, the worker refuses routine jobs against it. You can't re-run provisioning. You can't re-issue a handover link. The platform can no longer walk back in through the front door.

Why this matters: normally you'd protect a dangerous operation by requiring two different administrators to approve it. With exactly one operator account, that isn't possible — and the team decided that pretending otherwise would be worse than not having it. So sealing plus an audit trail is what replaces it. Getting back in afterwards is deliberately loud, slow, and separately recorded.

Notice where the seal is written

The console flips the status to active, but it does not write the seal — it holds no permission to. A permission that lets you set a seal also lets you clear it, and an unsealed school can have provisioning re-run over its administrator. So the one control that closes the door is deliberately not held by the process most exposed to the internet. The worker does it, through the queue.

15

The life of an organisation

Heads up — this is half-built

suspended works at the gateway, but there is no button anywhere to set it, no job kind for it, and no code that signs people out when a school is switched off. If you flip it by hand in SQL: traffic stops within 60 seconds, but everyone already logged in keeps their session for up to 12 hours. The companion document covers what to build.

Inside one service — the same seven folders every time

In one sentence

Data flows one direction only: routes → controllers → services → repositories → database. A build check fails if you break the arrow.

Checks that run in CI and will fail your build

CommandWhat it refuses
verify:layersThe two rules above.
verify:no-raw-sqlAny $queryRaw or SQL string in the service runtime. Queries go through the ORM.
verify:platformThe frontend gaining a database URL, a signing key, or the gateway token.

Run everything with npm run verify:all. Spin up the throwaway database first:

bash backend/tools/verify/compose.sh up

Never point a verification run at a shared database. The guards refuse, but the habit is what matters.

18

What breaks if something goes down

The reason the console is on that list: the Auth service asks it "which school is this hostname?" on every single request, without caching the answer. The gateway asks the same question but remembers the answer for 60 seconds and keeps serving a stale one if the console is unreachable. Auth does neither.

The companion document works through why that second lookup is redundant and what to do about it.

Part 6 — Why it was built this way

19

The decisions, and the reasoning behind each one

Thirty decisions that shaped this system. Most of them cost something — that's what makes them decisions rather than defaults.

About tenancy

01One database per organisation, not a tenant_id column

Why
A shared table means every query must remember a filter. One forgotten WHERE leaks one school's salaries to another. Separate databases make that impossible rather than unlikely.
Costs
1,350 databases to migrate, back up and monitor. A whole worker program exists for this.

02The subdomain identifies the organisation

Why
The school is known before anybody types anything — which is what makes an Employee ID alone enough to sign in. 55,000 employees, most without email, don't need to also remember a school code.
Costs
Every organisation needs a hostname in DNS and in the registry.

03The hostname is resolved against a registry, never by splitting the string

Why
A hostname arrives from the internet and can be anything. A registry lookup can't be steered by an attacker; host.split('.')[0] can.
Costs
A lookup on the request path — which is where the problem in chapter 18 comes from.

04Every connection asks the database which organisation it is

Why
It's the last line of defence. If everything upstream got confused, this still fails closed. It's the check that turns "we're careful" into "it cannot happen".
Costs
One extra statement per connection. At four connections per authorization, that adds up — see the companion document.

05An unknown organisation status becomes 404, never "allow"

Why
A new status added to the registry, or a typo, must not accidentally start serving data. The failure mode of getting this backwards is serving a school during exactly the state that exists to stop that.
Costs
Adding a status means remembering to map it, or it silently 404s.

About the frontend

06The browser calls the services directly; the Next server does not

Why
The old way had the Next server forging six headers on every call — which meant it had to hold the shared secret. Now the browser calls /api/… on its own address and the gateway adds the proof. The frontend needs no secret at all.
Costs
Screens are client-rendered, so there's no server-side data fetching to lean on.

07The frontend holds no credential of any kind, and a build check enforces it

Why
It's the most exposed part of the system. A rule nobody enforces is a rule that erodes — so verify:platform fails the build if a database URL, signing key or gateway token reappears in frontend/.
Costs
Anything needing a secret must become a backend endpoint.

08Nothing in the session payload is proof of anything

Why
It's unsigned JSON a client can fake. If a service branched on designationCode, permissions would live in two places and one day disagree. A screen uses it to decide what to draw; the service decides what happens.
Costs
Screens must handle the case where they drew a button the service then refuses. That's normal, not a bug.

About login and sessions

09The session cookie is signed, and a session id alone is worthless

Why
The signing key lives in the app's environment, never in the school's database. Steal the entire database and you get live session ids you still can't turn into a working cookie.
Costs
The key must be managed and rotated outside the database.

10The cookie carries the school's own key id

Why
A cookie minted for one school doesn't verify at another. Origin separation already stops the browser sending it; this makes it useless if it ever is.
Costs
Verifying needs one read of the school's signing_key_id — which is a per-school constant nobody caches yet.

11The __Host- prefix, and never a Domain attribute

Why
Every school is a subdomain of the same parent. A Domain-scoped cookie set by one would be sent to all of them. The prefix makes that impossible at the browser, not by convention.
Costs
The cookie must be Secure — fine, because browsers treat localhost as secure in development too.

12SameSite=Lax, plus an explicit same-origin check on every mutation

Why
Strict would break arriving from an external link already signed in. Lax permits a top-level cross-site POST, so every unsafe method also gets a real same-origin check rather than trusting the cookie policy alone.
Costs
One more middleware on every write route.

13Two cookies: a live session, and a 10-minute permission cache

Why
The session is checked against the database every request, which makes "ending someone's posting ends their access" true immediately. The token is only a shortcut, so grant changes are stale for at most ten minutes and session revocation is instant.
Costs
Two things to keep in sync. And the token is currently ignored by the endpoint that would benefit from it most.

14Rate limits are spent before the password is checked

Why
Counting after the work is a limit an attacker never reaches, because failures are what they're producing. Two separate buckets — one per IP, one per Employee ID — because "one address, many accounts" and "many addresses, one account" are different attacks.
Costs
Two checks before every login, even legitimate ones.

15An unknown Employee ID is checked against a fake password anyway

Why
Otherwise response timing tells an attacker which IDs are real, without a single password guess.
Costs
Wasted CPU on every bad login. Worth it.

16The failure count and the account lock happen in one statement

Why
Read-then-write lets a few hundred parallel guesses all read "4 failures" and none of them trigger the lock.
Costs
A slightly harder SQL statement to read.

About permissions

17Only Auth answers "may they?", and no service caches the answer

Why
Two copies of the permission rules is two chances to disagree, in the part of the system where being wrong matters most.
Costs
An HTTP call on every gated request. This is the single biggest performance cost in the platform, and it's deliberate.

18Authority comes from the active posting only — never a union

Why
The same human at a school and at a regional office is a different authority. Combining them would silently grant regional powers inside a school.
Costs
Users must switch chairs explicitly, and everything cached must be re-fetched after they do.

19A grant carries what may be done AND which rows it covers

Why
Returning a plain yes/no threw away the second half. "May appoint at headquarters" and "may appoint anywhere" are not the same permission.
Costs
Callers must handle a list, not a boolean.

20The bootstrap exception closes itself

Why
A new school has no dashboards, so nobody could set it up. The organisation administrator's own post can do a few things — but only until the first dashboard is published, after which the exception is gone. Every use is audited.
Costs
One extra branch in the permission check, and a query when it's reached.

21/internal/authorize returns 200 even for a refusal

Why
A refusal is a successful answer. A 403 here would leave the calling service unable to tell "you may not" from "I couldn't ask" — and those need completely different handling.
Costs
Callers must read the body, not just the status.

22An unauthorised internal caller gets 404, not 401

Why
401 confirms the endpoint exists. 404 means nobody can discover it by probing. The same trick is used for unknown organisations.
Costs
Harder to debug a misconfigured token — which is why the code logs a warning when it happens.

23Both allowed and refused decisions are written to the audit log

Why
A trail holding only refusals can't answer "who read this last month" — which is the question actually asked after an incident. But menu-drawing probes are not recorded, or millions of meaningless refusals would bury the real signal.
Costs
An insert on the critical path of every decision.

About services

24Each service logs into the database as itself

Why
The old way used one shared login that switched roles after connecting — so between connecting and switching, the connection held every module's permissions. One missed switch and helpdesk could read student records. Now the role is whatever PostgreSQL granted at login; there's no window and nothing to forget.
Costs
One database user and password per service to provision.

25The seven folders, with the arrow enforced by a build check

Why
Knowing one service means knowing all of them. Two rules fall out and both are checked: a service never sees a Request (so it can't read a header and pick a school), and a repository never sees a Verdict (so it can't decide which rows someone may see).
Costs
More files for small features.

26Routing by path prefix, from one environment variable

Why
A prefix that isn't listed falls through to the shell, so one feature can be extracted into its own service at a time. The browser can't tell the difference, and no shared file needs editing.
Costs
A typo in that variable looks exactly like a service that was never deployed — so a malformed entry refuses to boot.

About the control plane

27The control plane holds no tenant personal data, ever

Why
There is one operator account. If it's breached, the damage must stop at the registry. An attacker learns which schools exist, not who works there.
Costs
The operator console can't show anything useful about a school's people, even when that would be convenient.

28Two database roles, and the queue is the only channel

Why
The console is the internet-facing half, so it holds the least. It can enqueue a job kind from a fixed list with a simple payload — it never says how. The worker derives every database and role name itself and ignores what the job claims. A console that could name a role could grant that role access to a school's employee list.
Costs
Everything the operator does is asynchronous. No immediate feedback.

29Sealing replaces two-person approval

Why
With one operator, "two approvals from different administrators" isn't achievable — and claiming it would be worse than not having it. So once a school has a real administrator, routine jobs against it are refused. A database owner can't be prevented from acting, but re-entry becomes loud, slow and separately recorded.
Costs
Legitimate re-provisioning needs a deliberate break-glass path.

30Audit intent is written before the act, and provisioning is resumable

Why
An intent row with no outcome, or a success with no preceding intent, is itself the alarm. And a provisioning run that dies at step 4 of 7 resumes at step 4 — it doesn't start over, and it never leaves a half-built school nobody can see.
Costs
Two writes per operation, and every step has to be individually idempotent.
20

Known gaps — things that are not finished

Every project has these. Knowing them on day one saves you from assuming something works.

GapWhat it means for you
Auth calls the control plane on every requestThe biggest architectural issue. It makes the admin tool a hard dependency of the whole platform. Covered fully in the companion document.
The on/off switch is half-builtsuspended works at the gateway; nothing sets it, and nobody gets signed out. Don't assume you can switch a school off.
No real secrets managerThe worker writes generated database passwords to files. owner_secret_ref is a pointer by design, but nothing resolves it yet.
The audit trail isn't shipped anywhereIt lives in the same database whose owner it's meant to hold accountable. Until it's shipped out, the append-only rule is a speed bump, not a guarantee.
PIS integration is a stand-inWhat sits behind the personnel port today is a development placeholder. Ask before depending on staff data.
Nothing syncs Auth's copiesAuth keeps its own copies of the office hierarchy and designations. When the real ones change, nothing pushes the update.
Enrolment at scale is unsolved55,000 employees, most with no password and effectively no email. Getting them all their first login is an open problem.
IP allowlisting and WebAuthnOperator login is password + TOTP today. WebAuthn is the target and the schema has room for it.
