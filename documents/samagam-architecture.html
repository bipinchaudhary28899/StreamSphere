The good news

The worker — the piece with the most dangerous credential on the platform — is already off the request path entirely. It listens on no port and its only input is a job queue. You can stop it for a week and every school keeps working.

02

High-level design

Every organisation is one hostname. That hostname is the only thing that says which organisation a request belongs to, and turning it into an answer is the gateway's whole job.

The three rules that follow from the picture

  1. The database is the tenant boundary. No table carries a tenant column. Which database opens is decided from what the gateway proved, and asserted again by the database itself before any query runs.
  2. Authority is answered in one place. A service asks Auth/IAM and renders the answer. There is no second copy of may(), and no service caches a verdict.
  3. The frontend holds no credential. Not a pool, not a signing key, not the gateway's secret. The browser calls the services on the organisation's own origin, and the gateway supplies the proof. A build check fails if that changes.

04

Data flow — what is stored where, and why

Two kinds of database, and a deliberate rule about what may live in each. The control plane knows an organisation exists and which database holds it. It does not know who works there.

Why the split is drawn there

There is one platform operator account. If it is breached, the damage has to stop at the registry. That single constraint produces everything above: no tenant personal data, two database roles rather than one, a job queue as the only channel from console to worker, and an audit row written before the act so a missing intent is itself a signal.

It also produces the thing worth protecting in any redesign: the control plane creates organisations and does not use them. The current request path quietly violates that sentence, which is the subject of the next two sections.

05

Why every request goes through the gateway — and why that is right

The gateway is doing five jobs that genuinely cannot be done anywhere else:

  1. It is the only place a raw Host header meets the registry.The hostname arrives from the internet and is attacker-influenceable. Resolving it against a registry — rather than splitting the subdomain — is what makes tenant selection something an attacker cannot steer.
  2. It fails closed.A status it does not recognise resolves to 404, never to "allow". A new lifecycle state added to the registry cannot accidentally start serving data.
  3. It is the sole root of tenant trust.Downstream, x-forwarded-host is believed only when it arrives with x-gateway-token. Nothing else on the platform can name an organisation.
  4. It routes by path prefix, so services move one at a time.SERVICE_ORIGINS=helpdesk=…,sis=…. A prefix that is not listed falls through to the shell. Adding a service to a deployment is one environment entry and no code change.
  5. It is why the frontend holds zero secrets.The browser calls /api/… on the organisation's own origin and the gateway adds the proof. Before this, the Next server had to forge six headers on every call and therefore had to hold the shared secret.
Verdict

Keep it. The pattern is right and the implementation is careful — the status map, the stale-on-error cache, the request-id sanitising and the origin: null handling are all things that get discovered the hard way. Four things are worth fixing, and none of them is the design (§08).

06

Why every request also goes through the control plane — and why it shouldn't

The gateway hop is legitimate. The second lookup, inside Auth/IAM, is the one you are paying for, and it buys nothing. Here is the argument the code itself makes for it:

“A hostname is attacker-influenceable; a registry lookup is not.”

True in general — but not at this hop. Look at what Auth resolves from:

Three more facts that settle it

  • organisation() does not check status — only that the lookup succeeded, and the schema version. The gateway's verdict is the sole status gate, and a suspended organisation never reaches Auth. Removing the second call loses no check.
  • schemaVersion is the only fact Auth uniquely consumes. The gateway already fetches it on the same call — and discards it.
  • There is a third defence underneath both: every connection asserts tenant_key against the slug before any query runs, and throws TenantMismatch otherwise. A forged slug fails closed there regardless.
What this costs you today

Every authorized API request, every login, every session check and every navigation fetch makes one HTTP round trip to a Next.js route on the operator console, which runs one SQL query on a pg pool capped at max: 10. At 1,350 organisations, that single process is the first thing on the platform that falls over — and when it does, the failure presents as “Auth is slow”, which has already cost one debugging session on this codebase.

07

Making an organisation survive a control-plane outage

You asked for the property directly: if the control plane is off, organisations keep running. Here is what it takes, in three tiers — and why caching alone does not get you there.

What happens today

ComponentControl plane unreachable…and the process restarts
Gatewaysurvives Serves the last known answer per host, indefinitely — “a stale answer beats an outage”.dead Empty cache → 503 REGISTRY_UNAVAILABLE for every organisation.
Auth / IAMdead No cache at all. The next request is 503 UPSTREAM_UNAVAILABLE. Nobody signs in, nothing authorizes.dead
Domain servicesdead Not directly — but every gated route needs Auth, and Auth is down.dead
Workern/a Not on the request path.n/a

Tier 1 — cache in Auth the way the gateway already does do this first

Lift the TTL-plus-stale-on-error resolver out of the gateway and use it in Auth. Control-plane traffic drops from per request to roughly one call per minute per hostname, and Auth survives a restart of the console.

Cost: about a day. Tradeoff: the one the gateway already accepted and documented — a suspended organisation keeps serving for up to one TTL, which is why suspension must revoke sessions too (§09).

Tier 2 — the gateway forwards what it already resolved the clean fix

The gateway resolved the tenant and threw it away. Forward it under the same proof it already sends:

'x-gateway-token':    INTERNAL_TOKEN,   // already sent
'x-forwarded-host':   host,             // already sent
'x-tenant-slug':      tenant.slug,      // new
'x-tenant-public-id': tenant.publicId,  // new
'x-tenant-status':    tenant.status,    // new
'x-tenant-schema':    schemaVersion,    // new — keep it in the cache entry
  1. Set them unconditionally.They are spread after the inbound headers, so always-setting is what stops a client injecting its own.
  2. trustedTenant reads them into req.ctx.tenant.Same function, same token check, one more field group.
  3. authorizeViaAuth passes them through.This is the one that matters — the service→Auth hop is where the uncached call fires. Without it, Auth falls straight back to the control plane.
  4. organisation() uses them when present, resolves when absent.Keep the fallback: tests and direct calls have no gateway in front.

Result: the control plane is touched roughly once a minute per hostname, by the gateway alone. Auth and every org API behind it never touch it.

Tier 3 — the property you actually asked for the end state

Tiers 1 and 2 still leave one hole: a cold start during an outage. A gateway that restarts while the console is down has an empty cache and answers 503 for everyone. Caching cannot fix that, because a cache has nothing in it yet.

The registry is about 1,350 rows that change a few times a month. Treat it as data you ship, not a service you call:

OptionSurvives a CP outageSurvives a cold start during oneNotes
HTTP + per-process cache (tiers 1–2)Yes, while warmNoCheap, and worth doing regardless.
Signed tenant manifest
CP publishes a signed JSON snapshot; the gateway loads it at boot and refreshes on a timer or a webhook		Yes, indefinitelyYesrecommended 1,350 rows is a small file. The CP can be down for days. Signature keeps the registry authoritative.
Read replica of samagam_controlYesYesMakes the gateway a database client again — the thing this architecture spent effort removing.

And split the internal API off the console

Whatever you choose above, do this too. The two /api/internal/* routes are roughly 150 lines of SQL and a token check, sitting inside the operator UI. As long as they live there, a console deploy is a production outage. Moving them into a small separate process — or a second deployment of the same package — decouples operator-console availability from platform availability, and costs almost nothing.

What not to change: the status→HTTP map, the stale-on-error fallback, the request-id sanitising, the origin: null strip, and the decision to verify no tokens and open no database at the edge. Those are the parts that make the gateway safe to run at the perimeter.

09

The on/off switch — what exists, and what happens to people who are logged in

You asked what happens when a customer says “we don't want your service any more” and someone flips the switch. The honest answer is that there is no switch yet — only the half of it that refuses traffic.

PieceState
cp.tenant.status = 'suspended'exists A valid value in the schema's CHECK constraint.
Gateway refuses a suspended organisationexists 403 TENANT_UNAVAILABLE — deliberately not 404, because the people who work there need to know it exists and to ask an administrator. Tested.
A console action to set itmissing No suspend or resume anywhere in the operator UI.
A suspend_tenant job kindmissing The queue's CHECK constraint does not allow one.
Organisation-wide session revocationmissing revokeSession is per-session only; its callers are logout and password change.

What actually happens if you flip it by hand today

They are two different operations — name them separately

PauseCut off
MeaningNon-payment, a dispute, a maintenance window. You expect to turn it back on.Contract ended. Access should stop and not resume by accident.

What to build

  1. Two job kinds: suspend_tenant and resume_tenant.Widen the cp.job CHECK constraint. The payload carries a slug and nothing else, as every other kind does.
  2. A console action that writes the status and enqueues the job.Audit intent before the act, as the console already does everywhere else.
  3. A worker step that revokes, for the cut-off case only.UPDATE identity.session SET revoked_at = now(), revoked_reason = 'tenant_suspended' WHERE revoked_at IS NULL, inside the organisation's own database. One statement, one index.
  4. Cache invalidation, or accept the 60 seconds.For a pause, 60 s is fine. For a cut-off it is not — call resolver.forget(host) on every gateway, or bump the manifest version from §07.
  5. Decide the in-flight policy and write it down.Requests already proxied complete normally. That is almost certainly what you want; it should still be a decision rather than an accident.
One caveat the README already states

“Suspension is not a security control on its own and the sessions are revoked as well.” The first half is implemented; the second half is not. Until step 3 exists, a suspended organisation is a closed front door with everyone still inside.

10

Login and the token flow

Signing in

  1. Browser POSTs /api/auth/login on the organisation's own origin.No organisation is typed or chosen — the subdomain already says which one it is, which is what makes an Employee ID alone sufficient.
  2. Gateway resolves the host, allows, and routes /api/auth → :3110.Adds x-forwarded-host, x-gateway-token, x-request-id.
  3. Auth: trustedTenant → sameOrigin → organisation().The last of those is the control-plane call from §06.
  4. Two throttle buckets are spent before anything expensive.Per-IP and per-login-id — one address against many accounts and many addresses against one account are different attacks, and either limit alone leaves the other unthrottled.
  5. argon2 verification, through a gate of 4 concurrent hashes.An unknown login id verifies against a decoy hash so it costs the same time. Telling somebody which half was wrong is telling them half the answer.
  6. Failure count and lock happen in one statement.Read-then-write would let hundreds of parallel guesses all read “4 failures” and none of them lock.
  7. A session row is written, and two cookies are set.Absolute ceiling 12 hours; idle window 90 minutes, bumped by every authenticated call.

The two cookies

CookieShapeLifeWhat it is for
__Host-samagam_session sid . keyId . hmac
sid is identity.session.id — the payload, not the secret. keyId is that organisation's signing_key_id. The HMAC key lives in the application environment and never in the organisation's database.		 12 h The anchor. Checked against the database on every request, which is what makes “ending a posting ends the session” true at once rather than at expiry. A stolen copy of the database yields live session ids that cannot be turned into a working cookie.
__Host-samagam_at Signed token carrying tenantKey, tenantKeyId, employeeCode, sessionId, postingId, unitPath, reach and the full grants[]. Capped at 3,500 bytes; not issued if it would overflow. 10 min A cache of what the session may do. Minted at login and at posting switch — where authority changes — and nowhere else. Never authoritative.

Both are HttpOnly, Secure, SameSite=Lax, Path=/, and carry no Domain. The __Host- prefix makes the browser enforce that last part, which is the whole of the origin separation between organisations: every organisation is a subdomain of the same parent, so a Domain-scoped cookie set by one would be sent to all of them.

Every request after that

The service forwards the raw session cookie to /internal/authorize and believes the answer. It does not verify the signature itself — it could only check it against the key id the cookie names, which proves “the platform minted this” but not “for this organisation”. Auth verifies it against the resolved organisation's own key. That is why the signed cookie crosses the service boundary whole rather than as a bare session id, and why no domain service holds a signing key.

The rule that protects all of this

Nothing in the session payload is authorization evidence. Not designationCode, not isHead, not unitCode, not the presence of a user. A job title is not a permission — the permission is a node an administrator ticked, and only Auth knows whether they did. A screen decides only whether to draw something, from held[]; the service decides whether it happens.

11

Where the authorization cost actually is

The control-plane hop is the architectural problem. The database pattern is the throughput problem — and it is the cheaper of the two to fix.

One /internal/authorize opens four separate connections to the organisation's database, and each one re-runs the tenant assertion before doing its own work:

#CallStatementsCould it be avoided?
①signingKeyId(tenant)assertion + SELECT signing_key_idYes. A per-organisation constant that changes on key rotation. Cache it with an explicit invalidation.
②principalFor(tenant, sid)assertion + one indexed joinNo — keep it live. This is the read that makes revocation instant.
③may(tenant, principal, node)assertion + the live grant queryPartly. See the access token below.
④recordAccess(…)assertion + INSERT access_auditYes, off the critical path. It is awaited today and cannot change the verdict by design.

Four fixes, in order of value

  1. Collapse the four checkouts into one.Wrap decide() in a single connection and pass the handle down. Four checkouts and four assertions become one. No security property changes — the assertion still runs, once, before any work. biggest win, lowest risk
  2. Take the audit write off the critical path.A bounded in-process queue with a flush on shutdown, not fire-and-forget — an audit row that vanishes on a crash is a real loss. But an INSERT that cannot affect the answer should not be adding latency to every decision.
  3. Use the access token the system already mints.grantsFor() already accepts verified-token grants, and /api/auth/navigation already uses them — but /internal/authorize ignores the token entirely and runs the live query every time. Passing it and using it for the grants half, while still reading the session row live, keeps instant session revocation and drops query ③. Caveat: the token is minted only at login and posting switch, so a dashboard edit that revokes a grant would take up to ten minutes to bite. That is exactly the trade the TTL was chosen for — but make it a decision, not an accident.
  4. Remove the control-plane hop.§07, tiers 1 and 2.

What to preserve while you do it

The live session read on every request. It is the reason “ending a posting ends the session” is true immediately rather than at token expiry, and it is the property that makes the ten-minute grant TTL acceptable in the first place. Optimise around it, not through it.

The one-sentence summary

The architecture is right — a registry that owns tenant identity, a gateway that proves it, one database per organisation, and one place that answers “may they”. Do not rebuild it. Three narrow things are wrong: Auth asks the registry a question the gateway already answered, one decision opens four database connections where one would do, and the off switch has a front door with no lock on the inside. All three are local fixes, and none of them requires giving up a property the design was built to protect.
